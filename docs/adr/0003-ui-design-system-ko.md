# ADR-0003: UI 디자인 시스템 및 컴포넌트 전략

- **상태**: 제안됨 — 결정 대기. **[ADR-0001](0001-frontend-technology-ko.md)에 의해 차단됨.**
- **날짜**: 2026-09-18
- **이슈**: [#28 \[EVALUATION\]\[ADR\] UI Design System & Component Strategy](https://github.com/dasomel/beluga-manager/issues/28)
- **상위 에픽**: #1
- **관련 문서**: [ADR-0001](0001-frontend-technology-ko.md), [ADR-0002](0002-backend-api-technology-ko.md)
- **결정권자**: dasomel

## 배경

이슈 #28은 레이아웃/내비게이션, 타이포그래피/여백, 상태 및 헬스 인디케이터, 테이블, 카드, 폼,
토폴로지/그래프, 차트, 다크/라이트 테마, 접근성을 아우르는 디자인 시스템 및 공유 컴포넌트 전략을
요구한다. 명시된 원칙은 Narwhal 및 일반적인 관리 플랫폼 UX 패턴과의 일관성을 유지하면서도
**독립적인 Beluga Manager 브랜드 경험**을 구축하는 것이다.

**이 ADR은 구조적으로 ADR-0001에 종속된다.** 컴포넌트 라이브러리는 프레임워크별로 다르므로, 아래
선택지는 *조건부*로 프레임워크별로 정리되어 있다. 전문 컴포넌트, 라이선스 제약, 결정 요인과 같은
프레임워크 무관 항목만 #26과 독립적으로 정할 수 있다.

### 제품이 실제로 필요로 하는 것

#13–#21에 따르면 이 UI는 **밀도 높은 내부 운영 콘솔**이다. 기능적 밀도가 마케팅적 세련미보다
중요하지만, 여러 시간 사용해도 쾌적해야 한다. 구체적인 컴포넌트 목록은 다음과 같다.

| 필요 항목 | 출처 | 비고 |
|---|---|---|
| 앱 셸: 사이드바 내비게이션, 브레드크럼, 헤더, 사용자/로케일 메뉴 | #13–#21 | 모든 라이브러리에 기본 포함 |
| 상태 / 헬스 인디케이터 | #13, #14, #19 | 즉흥적인 색상이 아닌 **공유된 상태 어휘**가 필요 |
| 밀도 높고 정렬/필터/페이지네이션 가능한 테이블 | #14, #19, #20 | #43에 따라 서버 사이드 페이지네이션 및 필터링 |
| 가상화된 긴 목록 | #19 (이벤트, 리소스, 로그) | 대부분의 범용 라이브러리에는 없음 |
| 계층적 트리 내비게이션 | #15 (카탈로그 → 스키마 → 테이블 → 컬럼) | 흔하지만 대규모 트리를 처리해야 함 |
| **토폴로지 / DAG 그래프** | #16, #18 | **전문 영역 — 일반 UI 라이브러리에는 없음** |
| **구문 강조를 지원하는 SQL 에디터** | #17 | **전문 영역 — 일반 UI 라이브러리에는 없음** |
| 이벤트 타임라인 | #19 | 대개 자체 제작 |
| 로그 뷰어 | #19 | 가상화 필요; 대신 Loki로 외부 링크할 수도 있음 |
| 카드 / KPI 타일 | #13 | 기본 제공 |
| 폼, 확인 모달, 드라이런 미리보기 | #21 | 기본 제공되지만 파괴적 작업 패턴에 대한 규율이 필요 |
| 차트 (경량 사용) | #13, #19 | 요약 지표만; 무거운 분석 UI는 없음 — BI는 Superset이 담당 |
| 다크 / 라이트 테마 | #28 | 컴포넌트별 오버라이드가 아닌 토큰 수준의 관심사여야 함 |
| 접근성 | #28 | 키보드 내비게이션 및 스크린리더 시맨틱 |
| `en-US` / `ko-KR` 로케일 | README | 컴포넌트 수준의 로케일 팩과 날짜/숫자 형식 |

두 가지 결론이 즉시 따라온다.

1. **어떤 컴포넌트 라이브러리도 어려운 부분을 커버하지 못한다.** 그래프 렌더러와 SQL 에디터는
   어떤 디자인 시스템을 선택하든 전문 의존성으로 남을 것이며, 이를 맞춰 테마를 적용해야 한다.
   Beluga Manager를 차별화하는 시각적 표면의 약 3분의 1은 어느 쪽이든 자체 제작이다.
2. **상태/헬스 어휘는 Beluga 고유의 디자인 문제다.** `healthy / degraded / stale /
   unknown / unavailable`는 #13, #14, #19, #41, #42에 반복적으로 등장하며, API는 degraded와
   stale 상태를 명시적으로 표현하도록 요구된다. 상태 → 색상, 아이콘, 레이블, 툴팁, 접근 가능한
   이름으로의 매핑은 Beluga 자체 토큰에서 한 번만 정의되어야 하며, 라이브러리가 제공하는 severity
   색상을 즉흥적으로 가져와서는 안 된다. 색상만으로는 접근성과 그레이스케일/프로젝터 조건 양쪽
   모두에서 실패하므로 **비색상 인코딩은 필수**다.

### 구속 조건

- **에어갭 친화적**(`../architecture-ko.md`, 원칙 7): 런타임 CDN 없음, 원격 폰트 페치 없음,
  전화 홈(phone-home)하는 라이선스 서버 없음, 텔레메트리 없음. 폰트와 아이콘은 벤더링되어야 한다.
- **Apache-2.0 저장소**; #26은 OSS 라이선스를 명시적 기준으로 지정한다. **엔터프라이즈 데이터
  그리드 및 그래프 시장이 상용 라이선스에 지배되고 있기** 때문에 이 점은 평소보다 더 중요하다 —
  아래 함정 목록 참조.
- **Narwhal Portal은 UX 선행 사례이지, 컴포넌트 출처가 아니다.** #1, #18, #19, #20의 모든 참조는
  "reference"라고 명시하며 명시적인 재설계 언어와 함께 제시된다. #28 자체의 원칙도 *독립적인*
  Beluga 브랜드를 요구한다.
- **기존 디자인 자산 없음.** 이 저장소에는 로고 사용 가이드, 컬러 팔레트, 타입 스케일, Figma
  파일이 존재하지 않는다. 무엇을 선택하든 브랜드 레이어는 처음부터 시작한다.

### 피해야 할 라이선스 함정

다음은 흔히 추천되지만, dasomel이 의도적으로 상용 라이선스 예산을 편성하지 않는 한 Apache-2.0,
자체 호스팅, 에어갭 환경과 **양립 불가능**하다.

- **AG Grid Enterprise** — Community는 MIT이지만, 보통 필요로 하는 기능(그룹핑, 피벗, 고급
  필터, Excel 내보내기)은 상용이다. Community로 시작했다가 나중에 Enterprise가 필요해지기 쉽다.
- **Highcharts** — 비상업적 용도에 한해 무료이며, 그 외에는 상용이다.
- **yFiles, GoJS, Syncfusion, Kendo UI, DevExtreme** — 모두 상용이다.
- **Chart.js는 MIT로 문제없음**; **Apache ECharts는 Apache-2.0으로 문제없음**; **D3는 ISC로
  문제없음**.
- **Cytoscape.js (MIT)**, **React Flow / xyflow (MIT core)**, **Monaco (MIT)**, **CodeMirror 6
  (MIT)**, **TanStack Table/Virtual (MIT)** 모두 깨끗하다.
- **xyflow Pro**와 같은 "오픈 코어" 프로젝트는 일부 기능을 상용 티어 뒤에 두므로, 필요한 기능
  세트가 오픈 티어에 포함되는지 커밋 전에 확인해야 한다.

## 결정 요인

1. **밀도 높은 테이블 요구사항의 커버리지** — 제품에서 가장 많이 사용되는 컴포넌트.
2. **독립적인 Beluga 정체성 방향으로의 테마 적용성** — 라이브러리가 커스텀 룩에 얼마나 저항하는지.
3. **기본 제공되는 접근성 품질** — 포커스 관리, ARIA 시맨틱, 키보드 내비게이션.
4. **그리드와 차트를 포함한 전체 컴포넌트 세트의 라이선스 청정성**.
5. **에어갭 호환성** — 자체 호스팅 가능한 폰트/자산, 런타임 네트워크 의존성 없음.
6. **`ko-KR` 로케일 지원** — 내장 로케일 팩 대 직접 레이어 구축.
7. **번들 크기 및 트리 셰이킹** — 여전히 빠르게 느껴져야 하는 내부 콘솔임을 고려.
8. **전달 속도 대 장기적 통제력** — 이 ADR의 핵심 트레이드오프.
9. **유지보수 및 업그레이드 리스크** — 타인의 디자인 언어에서 발생하는 메이저 버전 변동.

## 검토한 선택지

### 프레임워크 무관 선결 사항: 전문 컴포넌트 계층

아래에서 무엇을 선택하든, 다음은 별도의 결정이며 대체로 프레임워크와 무관하다.

- **그래프/토폴로지**: Cytoscape.js (MIT, 강력한 레이아웃 알고리즘, 프레임워크 무관, #18의
  Kubernetes 인프라 토폴로지에 최적) 및/또는 React Flow (MIT, 최고 수준의 인터랙션과 커스텀 노드
  렌더링, React 전용, #16의 파이프라인 DAG에 최적). 완전히 맞춤형 레이아웃이 필요하다면 그 밑에
  D3 (ISC)를 사용.
- **SQL 에디터**: Monaco (MIT; 더 무겁고 VS Code급이며 뛰어난 SQL 지원) 또는 CodeMirror 6 (MIT;
  훨씬 가볍고 더 모듈화되어 있으며 테마 적용이 쉬움). 둘 다 지연 로드해야 함.
- **차트**: Apache ECharts (Apache-2.0) 또는 Recharts/Chart.js (MIT). 사용량은 경량 수준.
- **가상화**: TanStack Virtual (MIT) 또는 프레임워크의 동등 라이브러리.

### ADR-0001이 React를 선택하는 경우

#### 옵션 R1 — shadcn/ui (Radix primitives + Tailwind CSS), 저장소에 벤더링

일반적인 의미의 의존성이 아니다. 컴포넌트 소스 코드가 저장소로 복사되어 직접 소유된다.

**장점**

- **최대한의 테마 통제력**, 이는 #28의 "독립적인 Beluga 브랜드 경험" 요구에 부합한다. 맞서
  싸워야 할 상위 디자인 언어가 없다.
- **Radix primitives는 뛰어난 접근성**을 제공한다 — 포커스 트랩, ARIA 시맨틱, 키보드 인터랙션 —
  시각적 정체성을 함께 들여오지 않고도.
- **이상적인 에어갭 프로필**: 코드가 저장소에 있고, Tailwind는 로컬에서 컴파일되며, 폰트는
  선택적으로 벤더링된다. 런타임에 아무것도 페치되지 않는다.
- 오픈 코어 티어에 걸릴 일 없이 전 구간 MIT.
- 사용하는 것만 배포되며, 죽은 컴포넌트 무게가 없다.
- 업그레이드가 UI를 예기치 않게 깨뜨릴 수 없다. 상위 컴포넌트 버전이 존재하지 않기 때문이다.

**단점**

- **데이터 그리드가 없다.** 테이블은 TanStack Table (MIT)에서 오는데, 이는 완성된 그리드가 아닌
  헤드리스 엔진이다 — 정렬, 필터링, 페이지네이션, 컬럼 크기 조정, 선택 UI를 모두 직접 조립해야
  한다. 밀도 높은 테이블이 이 제품에서 얼마나 중심적인지를 고려하면 이것이 가장 큰 비용이다.
- **`ko-KR` 로케일 팩이 없고 날짜/숫자 형식 레이어도 없다.** 둘 다 `Intl`/`react-i18next` 위에
  직접 구축해야 한다. 관리 가능하지만, 배터리 포함 옵션이라면 이미 포함되어 있을 작업이다.
- 첫 번째 완성도 높은 화면까지 가장 느린 경로; 팀이 모든 컴포넌트의 버그를 직접 소유한다.
- Tailwind가 필요하며, 디자인 일관성은 이를 강제하는 라이브러리가 아니라 토큰 규율에 의존하게
  된다.
- 이를 채택하는 것 *자체가* 디자인 시스템을 설계하겠다는 약속이며, 시각적 결정을 내릴 누군가가
  필요하다 — 그런데 이 저장소에는 현재 디자인 자산도, 디자이너 시그널도 없다.

#### 옵션 R2 — Ant Design

**장점**

- **모든 옵션 중 가장 완전한 엔터프라이즈 컴포넌트 세트**이며, 진정으로 유능한 무료 테이블(정렬,
  필터링, 고정 컬럼, 확장 가능한 행, 행 선택) — MIT, 엔터프라이즈 티어 없음.
- **`ko_KR` 로케일이 내장**되어 있고, 날짜/숫자 형식 규칙, 폼 검증 메시지, 포괄적인 폼 시스템도
  마찬가지다.
- 밀도 높고 신뢰할 만한 관리 콘솔에 이르는 가장 빠른 경로; #13의 KPI 카드와 #14의 상태 배지에
  직접 대응하는 강력한 description/statistic/tag/badge 컴포넌트.
- 바로 이런 종류의 제품에 한국과 중국에서 매우 널리 사용됨; 채용 친화도가 높음.
- #15의 카탈로그 내비게이션에 적합한 트리 컴포넌트를 포함.

**단점**

- **재브랜딩에 적극적으로 저항하는 강하고 뚜렷한 시각적 정체성.** 디자인 토큰을 통한 테마 적용
  (v5+)이 크게 개선되었지만, Ant Design 앱은 대체로 Ant Design 앱처럼 보이는 경향이 있다 — 이는
  #28의 독립 브랜드 원칙과 직접적으로 충돌한다.
- 선택지 중 **가장 큰 번들 크기**; 트리 셰이킹이 도움이 되지만 기준선 자체가 무겁다.
- 완전한 오프라인 빌드를 위해서는 아이콘과 일부 자산에 주의가 필요하다.
- 접근성은 준수하지만 Radix 기반 접근 방식에 비해 가장 강한 강점은 아니다.
- 메이저 버전 마이그레이션이 역사적으로 상당한 작업이었다.

#### 옵션 R3 — Mantine

**장점**

- MIT, 사용 가능한 테이블을 포함한 매우 큰 컴포넌트 세트와 뛰어난 훅 라이브러리.
- **테마 적용이 일급 시민이며 문서화가 잘 되어 있다** — shadcn/ui보다 훨씬 많은 것을 제공하면서도
  Ant Design보다 리브랜딩이 상당히 쉽다.
- 좋은 접근성, CSS 변수 기반의 좋은 다크/라이트 테마(토큰 기반 상태 색상에 자연스럽게 맞음).
- 강력한 폼 처리, 알림, 모달, 날짜 컴포넌트; 날짜는 dayjs로 지역화된다.
- 속도 대 통제력 축에서 진정한 중간 지점.

**단점**

- 테이블은 Ant Design보다 가볍다; 밀도 높은 엔터프라이즈 그리드는 여전히 그 아래에 TanStack
  Table을 필요로 할 가능성이 높으므로, 가장 큰 컴포넌트 요구사항은 부분적으로만 해결된다.
- `ko-KR` 커버리지는 Ant Design의 내장 로케일 지원보다 얇다; i18n 레이어의 더 많은 부분을 직접
  구축해야 한다.
- React 자체가 시사하는 것보다 커뮤니티가 작음; 한국어 자료가 적음.
- 자체 CSS 레이어를 사용하므로, Tailwind도 원한다면 조정이 필요하다.

#### 옵션 R4 — MUI (Material UI)

**장점**

- 매우 성숙하고, 거대한 컴포넌트 세트, 뛰어난 TypeScript 지원과 문서.
- 강력한 테마 시스템; 우수한 접근성 실적; 한국어를 포함한 내장 로케일 지원.
- 매우 큰 채용 풀.

**단점**

- **Material Design은 의견이 강하고 즉시 알아볼 수 있는 시각 언어**다 — 이 옵션들 중 구글처럼
  *보이지 않게* 만들기가 가장 어려우며, 이는 #28의 독립 브랜드 목표와 충돌한다.
- **MUI X 라이선스가 함정이다**: 이 제품이 가장 필요로 하는 바로 그 컴포넌트인 데이터 그리드가
  오픈 코어다. `DataGrid`는 MIT이지만, `DataGridPro`/`DataGridPremium`(대규모 가상화, 그룹핑,
  트리 데이터, Excel 내보내기)은 상용이다. Pro 기능을 전제로 설계했다가 뒤늦게 라이선스 요구사항을
  발견하기 쉽다.
- Emotion 기반 런타임 스타일링은 매우 밀도 높은 테이블에서 성능 비용이 발생한다.
- 번들 크기가 상당하다.

### ADR-0001이 Vue를 선택하는 경우

- **Naive UI** (MIT) — TypeScript 우선, 매우 완전하며, 테마 적용성이 높고, 테이블이 강력함. 이
  제품의 요구사항에 가장 잘 맞는, Vue 진영에서 Mantine 포지션에 가장 가까운 옵션.
- **PrimeVue** (MIT) — 방대한 컴포넌트 세트와 진정으로 강력한 DataTable(Vue 생태계에서 가장
  강력한 무료 테이블)을 갖추었으며, 완전한 커스텀 테마를 가능케 하는 unstyled/pass-through 모드를
  제공.
- **Vuetify** (MIT) — 성숙하고 완전하지만, Material Design이 MUI와 동일한 브랜드 정체성 긴장을
  가져온다.
- **Element Plus** (MIT) — 성숙하고 밀도가 높으며, Ant Design과 유사한 트레이드오프 프로필을
  가짐.

Vue 경로는 **그래프** 결정을 상당히 바꾼다는 점에 유의해야 한다: 동등한 성숙도를 가진 Vue 네이티브
React Flow 대응물이 없으므로(`vue-flow`는 커뮤니티 규모가 더 작은 포팅 버전), Cytoscape.js 또는
D3 기반의 자체 제작 렌더러가 더 유력한 선택이 된다. 이는 ADR-0001로 다시 피드백되는 입력이다.

### ADR-0001이 Svelte를 선택하는 경우

- **Skeleton** (MIT, Tailwind 기반) 또는 **bits-ui / Melt UI** (MIT, 헤드리스 primitives —
  Radix/shadcn 접근 방식과 가장 가까운 Svelte 대응물).
- 컴포넌트 생태계가 세 프레임워크 중 가장 얇다; 특히 테이블 및 그리드 유사 컴포넌트를 훨씬 더 많이
  직접 구축해야 할 것으로 예상된다.
- 프레임워크 무관 전문 컴포넌트(Cytoscape, Monaco, CodeMirror, ECharts, D3)는 문제없이
  통합되므로, 전문 컴포넌트 계층이 문제가 아니라 기본 컴포넌트 계층이 문제다.

### 옵션 X — 완전 자체 제작 디자인 시스템 (프레임워크 무관)

컴포넌트 라이브러리 없이 헤드리스 primitives 위에 모든 것을 구축한다.

**장점**

- 완전한 브랜드 통제력과 제3자 시각적 결합이 전혀 없음.
- 사용하지 않는 컴포넌트 무게가 없는 최소한의 번들.

**단점**

- 매우 큰 비용이며, *반복적으로 발생한다*: 접근 가능한 메뉴, 콤보박스, 다이얼로그, 날짜 선택기,
  포커스 관리는 제대로 만들기 어렵고 미묘하게 잘못되기 쉽다.
- 일관성이 무너지는 것을 방지하려면 전담 디자이너와 실질적인 토큰/문서화 관행이 필요하다 — 디자인
  시스템의 정반대다.
- 요구사항에 의해 정당화되지 않는다. #28은 독립적인 브랜드 경험을 요구하는데, 테마가 적용된
  primitive 레이어만으로도 훨씬 적은 비용으로 이를 이미 달성한다.

논의를 마무리하기 위해 기록해 둔다; 이 규모의 팀에는 권장하지 않는다.

## 멀티모델 리뷰 (2026-09-21)

Codex(비평)와 Gemini(리서치)가 지금 Accepted 상태인 ADR-0001과 실제 저장소 상태
(`src/web/views/*.tsx`는 `mockData.ts` 위의 순수 Tailwind shell이고 컴포넌트 라이브러리는 전혀
설치되지 않음)를 기준으로 이 ADR을 검토했다. 표시된 부분은 WebSearch로 검증됨:

**R1(shadcn/ui)은 여전히 타당하고, "아직 아무것도 안 만들었다"는 사실이 이를 약화하지 않고
오히려 강화한다** — 지금 전환 비용은 사실상 0이며, 이 UI의 약 1/3(그래프, SQL 편집기, 타임라인)은
어떤 옵션을 택하든 bespoke이므로 독립 브랜드/air-gap/토큰 통제가 라이브러리의 컴포넌트 개수보다
더 중요하다. **다만 이 ADR은 R1의 실제 비용을 과소평가한다** — shadcn/ui는 완성된 design system이
아니라 소스 생성 방식이며, 팀이 테이블·날짜/숫자 포맷·페이지네이션·가상화·문서화·회귀 테스트를
계속 소유하게 된다. 실제 우선순위가 전담 프론트엔드/디자인 오너 없이 빠른 MVP라면 Ant Design이
더 나은 조건부 답이고, Mantine이 여전히 무난한 절충안이다. 아래 두 질문이 정확히 이 갈림길을
묻는다.

**버전/최신성 정정** (Gemini 보고를 WebSearch로 직접 재검증):
- **shadcn/ui**는 Tailwind v4(`@theme`, OKLCH 색상)와 React 19(`data-slot` 패턴)를 공식
  지원한다 — 이 저장소의 스택과 정확히 일치. CLI 설치는 설정 시점에 소스를 복사할 뿐 런타임
  종속성이나 CDN 호출이 없어 air-gap에 완전히 부합한다.
- **Ant Design** 현재 메이저 버전은 **v6**(2025년 말 출시)이다. `ko_KR` 로케일은 여전히
  내장돼 있으나 새로 추가된 컴포넌트는 번역이 늦게 따라올 수 있다. v5+/v6 디자인 토큰에도
  불구하고 기본 Ant 룩앤필에서 벗어나는(de-brand) 작업은 여전히 커뮤니티의 알려진 난제다.
- **Mantine** 현재 메이저 버전은 **v9**(2026년 상반기, React 19.2+ 필요)다. 이 ADR의 서술에
  대한 정정: `@mantine/core`에 내장된 `Table`은 **정렬·필터링이 전혀 없다** — Ant Design보다
  "가벼운" 정도가 아니라 스타일링된 `<table>` wrapper일 뿐이다. 실제 데이터 그리드가
  필요하면 별도 패키지 **Mantine React Table(MRT)**(TanStack Table v8 기반, 정렬/필터/
  페이지네이션/행선택/컬럼리사이즈까지 기능 완비 확인됨 — [문서](https://www.mantine-react-table.com/))이
  필요하다.
- **MUI X**: 오픈코어 경계는 그대로다(단일 정렬/기본 필터/페이징 = MIT `DataGrid`; 다중 필터/
  컬럼 고정/리사이즈/엑셀 내보내기 = 상용 `DataGridPro`/`DataGridPremium`), 다만 Gemini에 따르면
  2026년 4월경 Pro/Premium 가격 모델이 개발자 수 기준에서 애플리케이션 단위로 개편됐다 — MUI를
  다시 고려한다면 현재 가격을 재확인할 것.
- **xyflow(React Flow) 정정**: 코어 패키지는 실제로 MIT이지만, Pro 예제/템플릿은 별도
  라이선스를 가진다 — "xyflow 전체가 MIT"라고 구분 없이 쓰지 말 것
  ([xyflow open source](https://xyflow.com/open-source), [Pro license](https://xyflow.com/pro-license)).
- TanStack Table, Cytoscape.js, CodeMirror 6, Apache ECharts: 여전히 MIT/Apache-2.0이고
  오픈코어 함정 없음을 확인, 전부 Vite로 로컬 번들링되며 런타임 CDN 호출 없음.

**로그 뷰어(미해결 질문 6): 기본값은 Loki link-out** — 시간 범위/namespace/pod/workload를
보존한 딥링크로 Grafana Loki에 연결하고, Beluga에는 최근 이벤트/상태만 표시. 실제 인앱 요구가
확인되면 처음부터 커스텀 `@tanstack/react-virtual` 뷰어를 만들기보다 **`@patternfly/react-log-viewer`**
(Red Hat/PatternFly, npm에서 실존·활발히 유지보수 확인됨 — 가상화·ANSI·스트리밍 내장, 정확히
이런 Kubernetes 콘솔 용도로 만들어짐)가 더 적합한 출발점이다.

**빠진 Decision Driver**: 서버 측 필터/정렬과 대규모 데이터 성능; URL 딥링크와 브라우저 뒤로가기
동작; polling/stale/degraded 상태를 API 필드가 아니라 시각적으로 표현하는 방법; 컴포넌트
계층에서의 RBAC와 destructive-action 안전성; ops 콘솔을 위한 키보드 중심 운영성; 선택한
컴포넌트의 테스트 가능성; 브라우저 지원 기준; 그리고 선택한 컴포넌트/토큰의 장기 소유·업그레이드
정책.

**이로써 좁혀진 두 질문** (나머지는 저장소 사실로 이미 해결됨 — Tailwind는 이미 배포된 화면에서
쓰이고 있어 프로젝트 전역 사용이 이미 입증됨; 기존 Beluga/Narwhal 비주얼 아이덴티티는 로컬
`narwhal-portal` 저장소를 직접 확인한 결과 로고/팔레트/타입 스케일/Figma가 전혀 없고 사소한
테마 쿠키 헬퍼뿐이라 계승할 것이 없음으로 확인됨):

1. **전담 프론트엔드/디자인 오너 없이 빠른 MVP를 택할지, 독립적인 Beluga 브랜드에 투자할지?**
   결국 전담 오너가 있는지를 묻는 것이며, 이 저장소에는 어느 쪽으로도 신호가 없다.
2. **공식 접근성 목표**(예: WCAG 2.2 AA)가 있는지, 내부 도구로서 best-effort면 충분한지?
   공식 목표가 있다면 Radix 기반 옵션에 유리해지며, 어느 쪽이든 테스트 계획이 필요하다.

> ### 🏛 아키텍트 권고 *(참고용 권고 — 결정이 아님)*
>
> **ADR-0001이 React를 선택하는 조건부: 옵션 R1 — shadcn/ui (Radix + Tailwind), 벤더링 —
> 그리드에는 TanStack Table, 그래프에는 React Flow 및/또는 Cytoscape, SQL 에디터에는
> CodeMirror 6을 함께 사용.**
>
> **가장 결정적인 이유:** 실제로 구속력을 갖는 세 가지 제약 — 에어갭 배포, 전 구간에 걸친
> 허용적 라이선스, #28의 "독립적인 Beluga 브랜드 경험" — 이 모두 같은 방향을 가리키며, 벤더링된
> 소스는 구조적으로 이 세 가지를 모두 만족시킨다. 컴포넌트 코드가 저장소에 있으므로 런타임에
> 페치할 것이 없고, 뒤늦게 발견할 오픈 코어 티어도 없으며, Beluga 고유의 정체성을 구축하는 동안
> 맞서 싸워야 할 상위 디자인 언어도 없다.
>
> **보조 근거**
>
> - Radix는 진정으로 어렵고 잘못되기 쉬운 접근성 동작(#28은 a11y를 범위에 포함)을 시각적
>   정체성을 함께 들여오지 않고 제공한다.
> - 이 UI의 약 3분의 1 — 토폴로지 그래프, SQL 에디터, 이벤트 타임라인, 로그 뷰어 — 은 *어떤*
>   옵션을 선택하든 자체 제작이다. 200개의 컴포넌트를 제공하는 라이브러리도 이 부분에는 도움이 되지
>   않으며, 완전히 소유한 토큰 레이어가 있으면 제3자 테마를 역설계하는 것보다 전문 컴포넌트를 맞춰
>   테마화하기가 훨씬 쉬워진다.
> - Tailwind 토큰은 #42와 #43이 API에 표현하도록 요구하는 상태 어휘(`healthy / degraded /
>   stale / unknown / unavailable`)에 깔끔하게 매핑된다 — 하나의 정의를 배지, 그래프 노드, 테이블
>   셀, 차트가 동일하게 사용한다.
>
> **솔직한 반론과 그것을 택해야 할 조건:** 브랜드 독립성보다 작동하는 콘솔에 빠르게 도달하는 것이
> 더 중요하다면 Ant Design(R2)이 더 나은 선택이다 — 가장 구체적으로는 무료 테이블과 내장 `ko_KR`
> 로케일이 shadcn 경로의 두 가지 가장 큰 격차를 제거하기 때문이다. 팀이 한두 명이고 목표가 MVP의
> 가치를 빠르게 입증하는 것(#41의 명시적 목적)이라면, **Ant Design을 선택하고 Ant Design처럼
> 보인다는 사실을 받아들여라.** 어느 쪽 극단도 맞지 않다면, **Mantine(R3)이 방어 가능한
> 중간 지점**이며 전체적으로 2순위로 두겠다. 여기서 MUI는 권장하지 않는다. 주된 이유는 MUI X
> Data Grid의 오픈 코어 경계가 이 제품에서 가장 많이 사용되는 컴포넌트에 정확히 걸려 있기
> 때문이다.
>
> **위 선택과 무관하게 공통으로 권고하는 사항:**
>
> 1. **어떤 화면을 만들기 전에 상태/헬스 토큰 세트를 정의하라.** 상태 → 색상, 아이콘, 레이블,
>    접근 가능한 이름을 한 번만 정의하고 항상 비색상 인디케이터와 함께 사용한다. 이는 제품 내에서
>    가장 레버리지가 큰 단일 디자인 결정이며, 라이브러리의 것이 아니라 Beluga 고유의 것이다.
> 2. 완전한 IntelliSense급 SQL 자동완성이 필요하지 않다면 **Monaco보다 CodeMirror 6을
>    선택하라.** #17은 쿼리 워크스페이스를 Trino에 컨텍스트를 넘기는 진입점으로 설명하지,
>    완전한 IDE로 설명하지 않는다; CodeMirror는 훨씬 가볍고 테마 적용이 쉽다.
> 3. **그래프 결정을 뷰별로 분할하라.** React Flow는 #16의 파이프라인 DAG(커스텀 노드 렌더링,
>    인터랙션)에 적합하다; Cytoscape는 #18의 Kubernetes 토폴로지(더 크고 덜 선형적인 그래프에
>    걸친 실질적인 레이아웃 알고리즘)에 적합하다. 둘 다 사용하는 것은 방어 가능하다; 하나로 둘 다
>    억지로 처리하는 것은 그렇지 않다.
> 4. 첫날부터 **모든 폰트와 아이콘을 저장소에 벤더링하라.** CDN에 의존해 구축한 후 이를
>    되돌리는 것은 번거로우며, 이는 정확히 에어갭 원칙이 금지하는 것이다.

## 결과 및 영향

**벤더링/헤드리스 접근 방식(R1 또는 동등한 옵션)을 선택하는 경우:**

- 토큰 레이어를 먼저 정의해야 한다: 라이트/다크용 컬러 스케일, 타입 스케일, 여백 스케일, 반경,
  고도(elevation), 상태 어휘. 이는 후속 작업이 아니라 선결 조건이다.
- 시각적 결정을 누군가가 소유해야 한다. 이 저장소에는 현재 디자이너 시그널도 디자인 자산도 없다
  — 이는 기술적 문제가 아니라 인력 배치 문제다.
- 컴포넌트 인벤토리와 사용 문서가 필요하다. 그렇지 않으면 "시스템"이 일회성 컴포넌트 모음으로
  전락한다. 문서는 이 저장소의 이중 언어 규칙을 따라야 한다.
- 접근성은 가정이 아니라 검증되어야 한다: 테이블과 그래프의 키보드 탐색, focus-visible
  스타일링, 상태 인디케이터의 스크린리더 레이블.

**배터리 포함 라이브러리(R2/R3/R4 또는 Vue 동등 옵션)를 선택하는 경우:**

- 테마 작업은 라이브러리의 토큰 시스템에 선행 투입되어야 한다; 메이저 업그레이드에서 살아남지
  못하는 컴포넌트별 CSS 오버라이드는 피해야 한다.
- 전문 컴포넌트(그래프, 에디터, 타임라인)도 맞춰 테마를 적용해야 하며, 이는 색상을 하드코딩하는
  대신 라이브러리의 토큰을 읽는 것을 의미한다.
- 업그레이드 주기가 유지보수 약속이 된다; 이 라이브러리들의 메이저 버전은 단순한 버전업이 아니라
  마이그레이션이다.
- 오프라인 빌드를 명시적으로 검증해야 한다 — 아이콘, 폰트, 지연 페치되는 모든 자산.

**모든 경우 공통:**

- 그래프 렌더러, SQL 에디터, 가상화 라이브러리는 자체 라이선스 검토가 필요한 별도의 의존성이다;
  위에 나열된 함정들은 디자인 시스템과 무관하게 적용된다.
- 차트는 의도적으로 경량을 유지한다. Superset(6.1.0)이 플랫폼의 BI 도구이며, Beluga Manager가
  또 다른 BI 도구로 성장해서는 안 된다.
- 다크/라이트 테마는 처음부터 토큰으로 구현되어야 한다. 하드코딩된 색상 위에 테마를 나중에
  덧붙이는 것은 재작성이나 다름없다.
- 토픽명, 테이블명, 작업명, 네임스페이스 등 플랫폼 리소스 식별자는 주변 UI가 지역화되더라도
  README에 따라 절대 번역되어서는 안 된다.
- `ko-KR`에 대한 컴포넌트 수준의 로케일 커버리지는 옵션마다 크게 다르므로, 가정하지 말고 결정
  전에 실제 컴포넌트 목록에 대해 확인해야 한다.
