# ADR-0001: 프론트엔드 기술 선정

- **상태**: 제안됨 — 결정 대기
- **날짜**: 2026-09-18
- **이슈**: [#26 \[EVALUATION\]\[ADR\] Frontend Technology Selection](https://github.com/dasomel/beluga-manager/issues/26)
- **상위 에픽**: #1
- **관련 문서**: [ADR-0002](0002-backend-api-technology-ko.md), [ADR-0003](0003-ui-design-system-ko.md)
- **결정권자**: dasomel

## 배경

Beluga Manager는 현재 프론트엔드 코드가 없다. 저장소에는 정책 컴파일러(`src/`, TypeScript, Zod,
Vitest)라는 구현된 슬라이스 하나만 존재하며, [architecture 문서](../architecture-ko.md)와
[README](../../README-ko.md)에 기술된 Manager UI는 아직 계획 단계다.

구축할 프론트엔드는 공개 웹 서비스가 아니라 **내부 운영 콘솔**이다. 그 형태는 이미 등록된 UX
이슈들(#13–#21)에 의해 정해져 있다.

| 뷰 | 이슈 | 주요 컴포넌트 클래스 |
|---|---|---|
| 개요 대시보드 | #13 | 상태/KPI 카드 그리드, 헬스 배지, 드릴다운 링크 |
| 서비스 카탈로그 | #14 | 필터/정렬 가능한 목록, 상태 배지, 외부 UI 실행 링크 |
| 데이터 카탈로그 | #15 | 카탈로그 → 스키마 → 테이블 → 컬럼 계층형 내비게이터 |
| 파이프라인 및 작업 뷰 | #16 | **DAG / 플로우 그래프**, 작업 실행 상태 테이블 |
| 쿼리 워크스페이스 | #17 | 구문 강조 기능이 있는 **SQL 에디터**, Trino 컨텍스트 전달 |
| 아키텍처 뷰 | #18 | 헬스 오버레이와 노드 드릴다운이 포함된 **두 개의 인터랙티브 토폴로지 그래프**(데이터 파이프라인, Kubernetes 인프라) |
| 운영 | #19 | 리소스 테이블, 이벤트 타임라인, 로그 뷰어 / Loki 링크아웃 |
| 보안 및 정책 | #20 | 역할/권한 요약 테이블, 정책 목록 |
| 안전 작업(Safe actions) | #21 | 작업 폼, 확인 모달, 감사 추적 목록 |

따라서 이 결정을 지배하는 세 가지 역량 클래스는 **데이터 그리드**, **그래프/토폴로지 렌더링**,
**코드 에디터**이며, 그 외(카드, 폼, 배지, 타임라인)는 후보 프레임워크 어디에서나 범용적으로
제공된다.

이미 다른 곳에서 확정되어 여기서는 입력값으로 취급되는 추가 제약 조건들 — 미해결 질문이 아님 —
은 다음과 같다.

- **인증 필수, SEO 노출 제로.** 콘솔은 Keycloak SSO(`sso.local.beluga.internal`, Keycloak
  26.7.1, 플랫폼의 단일 아이덴티티 소스)를 통해서만 접근한다. 익명 방문자나 크롤러가 없으므로
  서버 사이드 렌더링은 검색 노출 이점도, 로그인한 운영자에게 유의미한 초기 렌더링 이점도 제공하지
  않는다.
- **에어갭(air-gapped) 친화성**은 상시 아키텍처 원칙이다(`docs/architecture.md`, 원칙 7): "의존성과
  런타임 자산은 셀프 호스팅 환경에서 통제 가능해야 한다." 런타임 CDN 호출, 원격 폰트 로딩,
  홈 콜백(phone-home) 텔레메트리는 완전히 비활성화 가능하고 오프라인에서 검증되지 않는 한
  결격 사유다.
- **배포 기반은 고정되어 있다.** 자매 프로젝트인 `beluga` 플랫폼은 `*.local.beluga.internal` 하의
  단일 APISIX 3.17.0 게이트웨이를 통해 HTTPS 443으로 모든 것을 제공하며, `selfHeal: true`를 사용하는
  ArgoCD GitOps로 배포된다. 새 런타임 프로세스는 모두 에어갭 레지스트리로 미러링되어야 하고
  `arm64`와 `amd64` 양쪽으로 빌드되어야 하는 새로운 컨테이너 이미지가 된다.
- **프론트엔드는 자격 증명을 보유해서는 안 된다.** 이슈 #22는 프론트엔드가 서비스별 자격 증명이나
  API를 직접 다루지 않으며 백엔드가 유일한 통합 지점임을 명시한다. 이는 ADR-0002에 대해서도
  구속력을 가지며 "SPA가 업스트림 OSS와 직접 통신"하는 선택지를 검토 대상에서 제외한다.
- **i18n은 초기 범위에 포함된다.** `en-US`와 `ko-KR`, 브라우저 로케일 감지, 영구 저장되는 사용자
  선택, 지역화된 날짜/숫자 포맷, 로케일 중립적인 API(지역화는 프론트엔드에서 수행 —
  `docs/architecture.md`, 원칙 4).
- **라이선스 위생.** 저장소는 Apache-2.0이며, #26은 OSS 라이선스를 명시적 평가 기준으로 명시한다.

**저장소 내에는 이전 프론트엔드 선호나 팀의 숙련도에 대한 신호가 전혀 없다.** 이슈 #1–#43 어디에도
프론트엔드 프레임워크, 차트 라이브러리, 그래프 라이브러리가 명시되어 있지 않으며, 저장소에는
프론트엔드 코드, 디자인 자산, 이전 시도의 락파일 증거가 전혀 없다. #1, #18, #19, #20의 Narwhal
Portal 언급은 일관되게 **참고할 UX 선행 사례**("참고")이며 항상 명시적인 재설계 표현과 함께
등장한다 — Narwhal의 코드나 컴포넌트를 재사용하라는 지시는 결코 아니다. 따라서 Narwhal의 스택은
여기서 제약 조건으로 취급되지 않는다. 만약 dasomel이 UX 영감이 아닌 컴포넌트 수준의 재사용을
의도한다면, 이는 이 ADR을 근본적으로 바꾸는 사항이므로 결정 이전에 명시되어야 한다.

## 결정 요인

1. **세 가지 난도 높은 컴포넌트 클래스 — 데이터 그리드, 토폴로지/DAG 그래프, 코드 에디터 — 에
   대한 생태계 깊이.** 후보들이 실질적으로 갈리는 유일한 기준이다.
2. **TypeScript 우선 적합성** — 저장소는 100% TypeScript(TS 7.0.2, Node ≥22)이며 ADR-0002도
   API를 TypeScript로 유지할 가능성이 높다. 엔드투엔드 타입 공유가 핵심 이점이다.
3. **호스팅의 운영 복잡도** — 기존 APISIX 게이트웨이 뒤에 위치한 정적 자산 방식과, 자체 이미지,
   Deployment, 프로브, 미러링이 필요한 추가 장기 실행 Node 프로세스 방식의 비교.
4. **에어갭 설치 가능성** — 오프라인 `npm ci`, 셀프 호스팅 폰트 및 자산, 런타임 CDN 없음, 강제
   텔레메트리 없음.
5. **OSS 라이선스 청결성** — 그리드와 그래프 라이브러리를 포함한 전체 의존성 경로에서 허용적
   라이선스(MIT/Apache-2.0/BSD/ISC)를 유지해야 한다. 상업적 라이선스는 보통 이 지점에서
   숨어 있다.
6. **유지보수성과 채용 시장** — 소규모 팀이 이를 인수인계할 수 있어야 한다.
7. **빌드/개발 서버 속도** — 부차적 기준이다. 최신 후보들은 모두 수용 가능한 수준이다.
8. **경계 보존** — 도구 선택이 #22의 프론트엔드/백엔드 분리 원칙을 위반하기 *쉽게* 만들어서는
   안 된다.

## 검토한 선택지

### 옵션 A — React + TypeScript + Vite (정적 SPA)

클라이언트 렌더링 SPA로, 정적 자산으로 빌드되어 게이트웨이(또는 최소한의 정적 컨테이너)를
통해 제공된다.

**장점**

- 난도 높은 부분에 정확히 대응하는, 허용적 라이선스를 가진 생태계 중 가장 깊은 선택지다:
  가상화된 그리드를 위한 TanStack Table + TanStack Virtual(MIT), DAG 및 토폴로지 렌더링을 위한
  React Flow / xyflow(MIT)와 Cytoscape.js(MIT), SQL 에디터를 위한 Monaco(MIT) 또는
  CodeMirror 6(MIT), 차트를 위한 Apache ECharts(Apache-2.0) 또는 Recharts(MIT). 이들 모두
  React에서 일급 지원되며 오프라인 설치가 가능하다.
- 패턴을 차용할 수 있는 Kubernetes/데이터 플랫폼 콘솔 선행 사례 풀이 가장 크다.
- 성숙하고 무난하며 잘 이해된 TypeScript 스토리를 제공하며, TanStack Query(MIT)가 #41/#42의
  "degraded/stale" 요구사항이 요구하는 폴링, 캐싱, stale-state, 리패치 시맨틱을 다룬다.
- 배포가 가장 저렴하다: 정적 파일 디렉터리 하나면 된다. 새로운 런타임도, 미러링할 새 이미지도,
  readiness 프로브도, CVE 패치가 필요한 Node 프로세스도 없다.
- 서버 계층이 없다는 점이 #22 경계를 실수로 위반하기 어렵게 만든다 — 업스트림 OSS 호출이 조용히
  쌓일 수 있는 서버 측 탈출구 자체가 없다.

**단점**

- React 자체가 Svelte나 Vue보다 더 많은 프레임워크 기반 코드를 포함하므로 번들 크기에 대한
  규율이 필요하다(라우트 단위 코드 분할, Monaco와 그래프 라이브러리의 지연 로딩).
- 배터리 포함(batteries-included) 대안들보다 보일러플레이트와 결정 사항이 더 많다. 상태 관리,
  라우팅, 폼 처리가 모두 별도의 선택 사항이다.
- 클라이언트 사이드 렌더링은 눈에 보이는 초기 로딩을 의미한다. 운영자가 계속 열어두는 인증된
  콘솔에서는 수용 가능하지만 실질적인 차이는 존재한다.
- 생태계의 폭이 넓다는 것 자체가 위험 요소이기도 하다 — 중복되는 의존성이 쌓이기 쉽다.

### 옵션 B — Next.js (SSR/RSC를 사용하는 React)

옵션 A와 동일한 React 컴포넌트 생태계에, 서버 런타임, 파일 시스템 기반 라우팅, 서버 컴포넌트,
라우트 핸들러가 추가된다.

**장점**

- 옵션 A의 모든 React 생태계 이점을 그대로 물려받는다.
- 서버 컴포넌트는 무거운 의존성을 클라이언트에서 배제하고 데이터 페칭을 중앙화할 수 있다.
- 라우트 핸들러는 세션/토큰 처리를 위한 편리한 지점을 제공하며, 서버가 존재하면 쿠키 기반
  인증이 더 단순해진다.
- 강력한 관례가 프로젝트별 결정 부담을 줄여준다.

**단점**

- **핵심 이점이 여기서는 적용되지 않는다.** SSO 뒤에서는 SEO가 무의미하고, 최적화할 익명 초기
  렌더링도 없으며, 대상은 소수의 인증된 운영자뿐이다.
- **두 번째 프로덕션 런타임을 추가한다.** 자체 이미지(arm64, amd64 빌드 필요), Deployment,
  프로브, 리소스 제한, 롤아웃 전략, CVE 패치, 에어갭 레지스트리 미러링이 필요한 Node 서버 —
  정적 파일만으로 처리할 수 있었던 콘솔을 위해 이 모든 것이 필요하다.
- **구조적으로 #22와 #34 위반을 유발한다.** 라우트 핸들러와 서버 컴포넌트는 프론트엔드 계층에서
  Kubernetes, Trino, Kafka를 "이번만" 호출하는 것을 지나치게 쉽게 만들어, Beluga Domain API를
  우회하는 섀도우 백엔드를 낳는다. AGENTS.md는 UI가 도메인 API를 우회하여 업스트림 OSS를
  직접 호출하는 것을 명시적으로 금지한다. 이를 막는 일이 아키텍처적 보장이 아니라 리뷰 규율의
  문제가 되어버린다.
- ADR-0002 역시 Node를 선택한다면, 플랫폼은 책임이 중복되고 경계가 모호한 **두 개**의 Node
  서비스를 갖게 된다.
- 에어갭 운영을 위해서는 의도적인 추가 작업이 필요하다: 텔레메트리 비활성화, 폰트 셀프 호스팅
  (기본 폰트 최적화 기능이 Google에서 폰트를 가져옴), standalone 산출물의 오프라인 동작 검증.

### 옵션 C — Vue 3 + TypeScript + Vite (정적 SPA)

**장점**

- `<script setup>`을 사용하는 Vue 3의 TypeScript 지원이 탁월하며 개발자 경험이 매우 우수하다.
- Vite는 Vue의 네이티브 빌드 도구다. 개발 서버와 HMR이 일급으로 지원된다.
- React보다 작은 런타임, 일반적으로 더 작은 번들, 더 완만한 학습 곡선.
- 밀도 높은 엔터프라이즈 테이블을 내장한 배터리 포함 컴포넌트 라이브러리가 강력하다(ADR-0003
  참조): Naive UI, PrimeVue, Vuetify, Element Plus.
- 한국어 문서화가 우수하고 한국 내 커뮤니티가 강하다 — 이 팀의 맥락에서는 실질적이면서도
  간접적인 유지보수성 이점이다.

**단점**

- 세 가지 난도 높은 컴포넌트 클래스에 대한 지원이 상대적으로 얇다. 그래프/토폴로지 선택지는
  대부분 프레임워크 독립적인 코어(Cytoscape, D3)를 감싼 Vue 래퍼이거나 `vue-flow`(React Flow의
  커뮤니티 포트, MIT, 더 작은 관리자 기반)다. Monaco와 CodeMirror는 프레임워크 독립적이라
  문제없이 통합되므로 에디터는 문제가 되지 않는다. **그래프 계층이 Vue의 통합 리스크가 더 큰
  지점이다.**
- TanStack Table에 Vue 어댑터가 있지만, Vue의 테이블 관행은 보통 "컴포넌트 라이브러리의 테이블을
  사용"하는 것이어서 데이터 그리드가 ADR-0003의 디자인 시스템 결정과 결합된다.
- Kubernetes/데이터 콘솔 관련 선행 사례가 더 적다.

### 옵션 D — SvelteKit (정적 어댑터, 또는 SSR)

**장점**

- 가장 작은 런타임과 대체로 가장 작은 번들. 뛰어난 원시 성능.
- `adapter-static`은 순수 정적 빌드를 만들어내며 옵션 A의 배포 방식을 유지하면서도, 필요성이
  생기면 동일한 프레임워크에서 이후 SSR을 추가할 수 있다.
- 보일러플레이트가 매우 적다. 빠르게 작성할 수 있고 TypeScript 지원도 좋다.

**단점**

- **정확히 난도 높은 부분에서 생태계가 가장 얇다.** React Flow에 필적하는 성숙도를 가진
  Svelte 네이티브 대안이 없다. 토폴로지 작업은 Cytoscape나 D3를 직접 래핑하는 것을 의미한다.
  가상화된 엔터프라이즈 데이터 그리드 역시 마찬가지로 직접 만들어야 하는 제안이다.
- 채용 시장이 가장 작고 Kubernetes 콘솔 관련 선행 사례가 가장 적다.
- Svelte 5의 룬(runes) 반응성 모델은 최근에 도입되어 일부 생태계 라이브러리가 아직 따라가지
  못하고 있다.
- SvelteKit을 선택하고 정적 어댑터만 사용한다면, 풀스택 프레임워크의 관례를 그 풀스택 이점
  없이 도입하는 셈이 된다.

### 옵션 E — Narwhal Portal의 스택과 컴포넌트 재사용

**장점**

- Narwhal의 컴포넌트가 실제로 재사용 가능하고 스택이 최신이라면 잠재적으로 큰 초기 이점을
  얻을 수 있다.
- #1이 목표로 명시한, 자매 제품과의 자동적인 UX 일관성을 확보할 수 있다.

**단점**

- **이슈 기록이 이를 뒷받침하지 않는다.** #1, #18, #19, #20의 모든 Narwhal 언급은 *UX를
  참고하라*는 것이며, Beluga의 데이터 플랫폼 성격에 맞춘 명시적인 재설계 표현과 함께 쓰인다.
  코드 재사용을 요구하는 내용은 없다.
- 이 저장소만으로는 평가할 수 없다 — Narwhal의 스택, 라이선스, 컴포넌트 품질이 여기서는 보이지
  않는다. 평가하려면 접근 권한과 별도의 스파이크가 필요하다.
- 다른 문제 영역(데이터 플랫폼의 토폴로지, 카탈로그, 쿼리 워크로드가 아닌 일반 플랫폼/운영
  포털)을 위해 선택된 스택을 그대로 들여오는 위험이 있다.
- #28이 명시한 원칙은 **독립된 Beluga 브랜드 경험**이며, 일관성은 관리 플랫폼 UX 패턴 수준으로
  한정된다 — 이는 컴포넌트 재사용이 아닌 패턴 재사용을 뒷받침하는 근거다.

## 결과 및 영향

**옵션 A(또는 그 외의 정적 SPA)가 선택될 경우:**

- 프론트엔드가 이 저장소 내 npm 워크스페이스로 존재할지, 별도 저장소로 존재할지에 대한 빌드
  시점 결정이 필요하다. `package.json`은 현재 워크스페이스가 아닌 단일 패키지다 — **이는 세부
  사항이 아니라 해결되지 않은 전제조건이다**(미해결 질문 참조).
- API 기본 URL은 재빌드 없이 SPA를 다른 대상으로 재지정할 수 있도록 빌드 시점 또는 런타임에
  설정 가능해야 한다. 부팅 시 가져오는 런타임 `config.json`이 에어갭 친화적인 일반적 해법이다.
- 인증은 기존 Keycloak 렐름(`sso.local.beluga.internal`)에 대한 PKCE 기반 OIDC 퍼블릭
  클라이언트가 된다. 토큰 저장, 사일런트 갱신, 로그아웃은 프론트엔드의 책임이며, 액세스 토큰은
  Beluga Domain API 호출에 첨부된다. 검증은 ADR-0002가 담당한다.
- APISIX는 콘솔 호스트(예: `manager.local.beluga.internal`)에 대한 라우트와 SPA 히스토리
  폴백(알 수 없는 경로 → `index.html`)을 추가로 얻는다.
- 첫날부터 번들 규율이 필요하다: 라우트 단위 코드 분할, 그리고 가장 큰 두 의존성인 Monaco와
  그래프 라이브러리의 지연 로딩.
- 모든 폰트와 아이콘은 저장소에 벤더링된다. 런타임 CDN 참조는 없다.

**서버 렌더링 옵션이 대신 선택될 경우:**

- 컨테이너 이미지, Deployment, Service, 프로브, 리소스 제한, ArgoCD 애플리케이션 항목이
  추가되며, arm64/amd64 빌드와 에어갭 레지스트리 미러링도 함께 필요하다.
- 서버 계층이 업스트림 OSS API를 직접 호출하지 못하도록 막는 명문화된 규칙(가급적 린트 규칙
  또는 CI 체크)이 필요하며, 이는 #22와 #34를 보존하기 위한 것이다.

**어느 쪽이든 공통으로:**

- ADR-0003(UI 디자인 시스템)은 **이 결정에 종속(gated)된다** — 컴포넌트 라이브러리는
  프레임워크별로 다르기 때문이다.
- i18n 라이브러리 선택은 프레임워크를 따른다(`react-i18next` / `vue-i18n` / `svelte-i18n`).
  README의 i18n 섹션에 따라 `en-US`와 `ko-KR`을 지원하고 사용자 선택을 영구 저장해야 한다.
- Kafka 토픽 이름, 테이블 이름, 작업 이름, 네임스페이스 등 플랫폼 리소스 식별자는 README에
  따라 절대 번역해서는 안 된다.

## dasomel 확인이 필요한 미해결 질문

1. **모노레포냐, 분리된 저장소냐?** 프론트엔드, Domain API, 기존 정책 컴파일러를 하나의
   npm-workspaces 저장소에 둘지, 별도 저장소로 둘지. #1–#43 어디에서도 이를 결정하지 않으며,
   이는 첫 프론트엔드 코드 커밋을 막는 전제조건이다.
2. **팀 구성과 기존 프레임워크 경험.** 이 ADR에서 가장 큰 미지수이며, 이 변수는 권고를 Vue
   쪽으로 정당하게 뒤집을 수 있다. 저장소 내에는 이에 대한 답이 없다.
3. **Narwhal Portal 재사용이 실제로 검토 대상인가?** 이슈들은 "UX를 참고하라"고 말한다. 만약
   코드나 컴포넌트 재사용이 진정으로 의도된 것이라면, 옵션 E는 Narwhal에 대한 접근 권한을 갖고
   실제로 평가되어야 하며, 이 ADR은 결정되기보다는 수정되어야 한다.
4. **에어갭 요구사항은 얼마나 엄격한가?** `docs/architecture.md`는 이를 원칙으로 명시하지만
   #1–#43의 어떤 이슈에서도 언급되지 않는다. 이것이 확고한 프로덕션 제약인지 지향점인지에 따라
   옵션 B의 미러링 비용이 갖는 비중이 달라진다.
5. **브라우저 지원 최저 기준이 필요한가?** 최신 에버그린 브라우저를 가정했다. 만약 잠금된 기업
   표준 브라우저 기준선이 존재한다면 빌드 타깃과 일부 라이브러리 선택에 제약이 생긴다.
