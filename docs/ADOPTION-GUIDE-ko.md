# Beluga Manager 도입 가이드

> Beluga Manager는 아키텍처 중심으로 계속 진화하는 프로젝트다. 이 가이드는 **구현된 vertical slice**와 목표 아키텍처를 의도적으로 분리한다.

## 1. 증거 수준으로 주장을 읽는다

도메인, 엔드포인트, UI 워크플로를 문서화할 때 세 가지 라벨을 사용한다:

- **Implemented(구현됨)** — 소스가 존재하고 워크플로를 실행/검증할 수 있다.
- **Integrated(연동됨)** — 구현됐고 의도한 Beluga/백엔드 경계에 대해 실제로 실행됐다.
- **Planned(계획됨)** — 설계/로드맵 단계일 뿐이며 현재 제품 동작으로 제시하지 않는다.

## 2. 첫 성공 계약

새 기여자는 구현된 도메인 하나를 골라 vertical slice를 증명할 수 있어야 한다:

1. 저장소의 현재 개발 경로로 manager를 실행한다.
2. UI/API 진입점에 도달한다.
3. 통제된 백엔드나 fixture에 대해 읽기 전용 도메인 오퍼레이션 하나를 실행한다.
4. 응답이 UI/API 표면에 올바르게 표현되는지 확인한다.
5. 검증에 사용한 command/test/build 증거를 남긴다.

프로젝트가 쓸모 있는 첫 성공을 내기 전에 목표 도메인 전부가 존재할 필요는 없다.

## 3. 아키텍처 경계

manager는 통합/관리 표면이며, Beluga 리소스의 문서화되지 않은 두 번째 진실 원천이 되어서는 안 된다. 설정, credential, 클러스터 오퍼레이션, 외부 API의 소유권은 명시적으로 유지해야 한다.

## 4. 문서 구조

우선순위: 현재 상태 → 실행 가능한 Quick Start → 첫 검증된 vertical slice → implemented/planned 매트릭스 → 아키텍처 → 도메인 세부사항 → 로드맵.

## 5. 유지보수 규칙

계획된 도메인이 구현으로 전환될 때마다 implementation matrix를 갱신하고, README나 블로그 콘텐츠에서 그 주장을 승격하기 전에 가장 작은 재현 가능한 검증을 추가한다.
